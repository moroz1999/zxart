# Translations and interface language

## The rule
- New user-facing text is **frontend-only**: `ngx-translate` keys in
  `ng-zxart/src/assets/i18n/{en,ru,es}.json`, all three languages filled in the
  same change. Hardcoded strings in templates and components are forbidden.
- **Backend translations are legacy and forbidden in new code**: the database
  records resolved at runtime by `translationsManager`, and the Smarty
  `{translations name="…"}` that reads them. No new keys, and no label assembled
  on the server — the API sends codes, the frontend names them.
- If new functionality looks like it needs a backend translation — a new key, or
  an existing one reused — **stop and ask the user** instead of adding it.

## Where the bundles live
- Source: `ng-zxart/src/assets/i18n/{en,ru,es}.json`.
- `composer build` builds into `htdocs/js/ng-zxart/` and copies `src/assets`
  over `htdocs/assets/`. The SPA loads `/assets/i18n/<lang>.json`
  (`environment.assetsUrl`, `app.config.ts`), so the copy under
  `htdocs/assets/` is the one actually served. Both are committed.

## Interface language

The SPA owns it. There is no language segment in SPA URLs and no reliance on the
backend session language.

The interface language is a **user preference** (`PreferenceCode::LANGUAGE`,
iso6393 value), so it flows through `UserPreferencesService` exactly like the
theme — see [features/language-auth.md](features/language-auth.md#preference-storage).
`LanguageService` (`features/settings/services/language.service.ts`) is the
single owner and mirrors `ThemeService`:

- The supported languages are a frontend constant (`SUPPORTED_LANGUAGES`)
  matching the shipped bundles. Each entry maps a short code (`en`/`ru`/`es`,
  used by ngx-translate) to a backend iso6393 code (`eng`/`rus`/`spa`), plus a
  native title and flag.
- `initialize()` applies the stored language immediately (the `language`
  preference from localStorage, or English by default), then calls
  `UserPreferencesService.initialize()` and re-applies the value fetched for a
  logged-in user. It registers the langs, sets the default lang, and calls
  `translate.use()`.
- `setLanguage(short)` (switcher) applies the language and persists it via
  `UserPreferencesService.setPreference('language', …)`. Anonymous visitors
  never send anything to the backend.
- `languageCode$` exposes the current iso6393 code; language-scoped API callers
  (comments, backend links) subscribe to it.

A logged-in user's stored language arrives through the usual
`/userpreferences/` fetch — it is **not** carried on the current-user response.
Both frontend and backend preference defaults are `eng`.

## Language on API requests

`languageInterceptor` (`features/settings/interceptors/language.interceptor.ts`)
adds an `X-Language` header (iso6393) to every same-origin request.
`LanguagesManager::applyRequestedLanguageHeader()` is the one place that reads
it, and every endpoint the SPA calls applies it, so responses are localized in
the selected language independent of the URL or session:

- `LoggedControllerApplication` calls it in its constructor, which covers every
  `ZxArt\Controllers\*` endpoint. It then re-syncs `publicStructureManager`'s
  element path restriction, which DI froze to the language current when it was
  built.
- `jsonElementDataApplication` calls it before it resolves the requested path,
  because the element data it serves — the software catalogue's categories,
  legal statuses and release types among them — is named in whatever language
  the elements are loaded in.

A response built this way is language-dependent as a whole. An API method whose
observable lives with the rendered view subscribes to `LanguageService.languageCode$`
and repeats the request with `switchMap`; the component consumes it through the
`async` pipe and uses ref-counted sharing when several consumers need the same
response. Short-lived requests such as pagination take the current language once
and are repeated by their owning component. Backend-named values are always
refetched after a language switch rather than relabelled in the frontend.

## Backend language detection

`LanguagesManager` keeps no server-side memory of the public language: it is
resolved per request from the URL segment (legacy pages only), the configured
default, and the `Accept-Language` header, in that order. Nothing is written to
a cookie or to the session.

The server-rendered admin panel is the exception: an explicit `?lang=` choice is
persisted by `LanguagesManager::persistAdminLanguageCode()` into the
`cl_adminLanguages` cookie and read back by the `adminLanguages` group only.

## Legacy keys still in use

- `zxRelease.filetype_*` — the prods-list format filter and the `/formdata/`
  option lists, see [features/release.md](features/release.md).
- Entity titles written per language are content, not interface text: category
  names, editorial pages, party compo names. They come from the elements
  themselves, localized by the request language.
- Comment texts are translated per language by the AI pipeline — see
  [features/comments.md](features/comments.md).
